# Skill Creator

スキルの新規作成と反復改善を支援するスキル。

全体の流れ:

1. スキルの目的と仕様を明確にする
2. SKILL.md のドラフトを書く
3. テストプロンプトで動作を確認する
4. フィードバックに基づいて改善する
5. 満足するまで 3-4 を繰り返す

ユーザーがこのプロセスのどの段階にいるかを判断し、そこから支援を開始する。
既にドラフトがあるなら直接テスト・改善に入る。「評価は不要、一緒にバイブスで作って」と言われたらそれに合わせる。

## Phase 1: 意図の把握

### Capture Intent

会話の中にすでにワークフローが含まれている場合がある（「これをスキル化して」など）。その場合は会話履歴から情報を抽出する — 使われたツール、ステップの順序、ユーザーが行った修正、入出力の形式。

以下を明確にする:

1. このスキルで Claude に何をさせるか
2. いつトリガーされるべきか（どんなユーザーの発話・文脈で）
3. 期待する出力形式は何か
4. 他のスキルやツールとの連携はあるか

### Interview & Research

エッジケース、入出力形式、成功基準、依存関係について積極的に質問する。
利用可能な MCP があれば、ドキュメント検索や類似スキルの調査に活用する。

## Phase 2: SKILL.md の記述

**記述前に `references/skill-standard.md` を読む。** ディレクトリ構造、frontmatter、Progressive Disclosure、description の書き方のルールが定義されている。

### スキルの構造

```
skill-name/
├── SKILL.md (必須)
│   ├── YAML frontmatter (name, description 必須)
│   └── Markdown 本文
└── Bundled Resources (任意)
    ├── scripts/    — 決定的・反復的な処理用スクリプト
    ├── references/ — 必要時にロードするドキュメント
    └── assets/     — テンプレート、画像等
```

### Progressive Disclosure

スキルは3段階で読み込まれる:

1. **Metadata** (name + description) — 常にコンテキストに入る（~100語）
2. **SKILL.md 本文** — スキル発動時に読み込まれる（500行以内が目安）
3. **Bundled resources** — 必要時にオンデマンドで読む（サイズ制限なし）

500行を超えそうなら `references/` に分離し、SKILL.md から「いつ読むか」を指示する。
300行を超える reference には冒頭に目次を付ける。

### description の書き方

description はスキルのトリガーを決める最も重要な要素。Claude はスキルを使わない方向に偏る傾向があるため、積極的（pushy）に書く。

**悪い例:**
> 調査レポートを作成する

**良い例:**
> テーマに基づいた構造化調査レポートをMarkdownまたはPPTXで作成する。「調べて」「レポートにまとめて」「報告書を作って」「○○について調査して」等の依頼では必ずこのスキルを使うこと。

ポイント:
- **何をするか** + **いつ使うか** の両方を書く
- トリガーとなるユーザーの発話パターンを列挙する
- 「必ずこのスキルを使うこと」のような強い表現を使う
- 曖昧な表現を避け具体的に書く

### 本文の書き方

- 命令形で書く（「〜してください」ではなく「〜する」「〜せよ」）
- 出力フォーマットはテンプレートとして明示的に定義する
- 入出力の具体例を含める
- **なぜそうするか** の理由を添える — MUST の連発より、理由を説明する方が効果的
- ドメインが複数ある場合は reference で分割する

**出力テンプレートの例:**
```markdown
## レポート構造
以下のテンプレートを使う:
# [タイトル]
## 概要
## 主な発見
## 推奨事項
```

**入出力例の書き方:**
```markdown
**Example 1:**
Input: JWTを使ったユーザー認証を追加
Output: feat(auth): JWT認証を実装
```

## Phase 3: テストと改善

### テストプロンプトの作成

ドラフト完成後、2-3個のリアルなテストプロンプトを作成する — 実際のユーザーが入力しそうな内容にする。ユーザーに確認してから実行する。

### テストの実行

各テストプロンプトについて:
- スキルありの実行（subagent でスキルパスを指定して実行）
- 必要に応じてベースライン（スキルなし）も実行

結果をユーザーと一緒に確認する。

### 改善の考え方

1. **フィードバックから汎化する**: テスト例だけに効く狭い修正ではなく、幅広いケースで機能する変更を行う。スキルは何度も使われる — テスト例への過剰適合は避ける

2. **プロンプトを lean に保つ**: 効果のない指示を削除する。トランスクリプトを読んで、スキルのせいでモデルが無駄な作業をしていないか確認する

3. **why を説明する**: ALWAYS や NEVER を全大文字で書くより、なぜそうすべきかを説明する方が効果的。LLM は理由を理解できるなら、柔軟に応用できる

4. **共通処理をスクリプト化する**: テスト実行で subagent が毎回同じようなヘルパースクリプトを書いていたら、それを `scripts/` にバンドルする

### 反復ループ

1. スキルを改善する
2. テストプロンプトを再実行する
3. ユーザーとレビューする
4. 以下のいずれかまで繰り返す:
   - ユーザーが満足した
   - フィードバックが空（問題なし）
   - 改善が頭打ちになった

## Phase 4: description の最適化

description はスキルがトリガーされるかどうかを決める主要なメカニズム。

### トリガーの仕組み

スキルは name + description で Claude の available_skills リストに表示される。Claude はこの description を見てスキルを使うか判断する。重要なポイント:

- Claude は自分で簡単に処理できるタスクにはスキルを使わない傾向がある
- 複雑で専門的なタスクほどスキルがトリガーされやすい
- description のキーワードと文脈の一致が重要

### 最適化の手順

1. **トリガー評価クエリを作成する**: should-trigger（8-10件）と should-not-trigger（8-10件）を用意する
2. should-trigger は同じ意図の異なる表現をカバーする（フォーマル、カジュアル、間接的な表現）
3. should-not-trigger は **近接ミス** を重視する — キーワードが重なるが実際には別のスキルが適切なケース
4. 実際に Claude に投げて、意図通りにトリガーされるか確認する
5. 結果に基づいて description を調整する

**良い評価クエリの例:**
- 具体的で詳細がある（ファイルパス、個人的な文脈、列名など）
- 実際のユーザーが入力しそうな自然な文章
- カジュアルな表現、略語、typo を含むものも

**悪い評価クエリの例:**
- `"データをフォーマットして"` — 抽象的すぎる
- `"フィボナッチ関数を書いて"` — 明らかに無関係（テストにならない）

## スキル改善チェックリスト

- [ ] frontmatter の name（64文字以内）/ description（200文字以内）は適切か
- [ ] description は十分に pushy か — トリガーフレーズを列挙しているか
- [ ] SKILL.md は500行以内か（超えるなら references/ に分離）
- [ ] 出力フォーマットがテンプレートとして定義されているか
- [ ] 入出力の具体例があるか
- [ ] references/ の読み込みタイミングが指示されているか
- [ ] why が説明されているか（MUST の連発になっていないか）
- [ ] 命令形で書かれているか
